# AES-CTR Decrypt 算子性能分析报告

## 1. 概述

基于 `PytorchInvocation/trace/` 目录下的 16 个 Chrome Trace 文件，对 `npu_aes_ctr_decrypt` 算子在 NPU 上的运行时间进行分析。测试用例涵盖 9 种数据 shape，数据均为 `uint8` 类型。

测试环境：
- CANN = 8.1.RC
- PyTorch = 2.1.0, Python = 3.9, AArch64

## 3. 首次调用（含JIT编译）耗时

算子在首次调用时需经过 JIT 编译（`torch_npu.npu.set_compile_mode(jit_compile=True)` 默认开启），耗时远高于稳态。

| Trace 文件 | 首次调用 (ms) | 后续稳态平均 (us) | 编译开销倍数 |
|------------|--------------|-------------------|-------------|
| chrome_trace_20250606_144720 | 82.68 | 102.27 | ~808x |
| chrome_trace_20250624_161806 | 78.93 | 102.12 | ~773x |
| chrome_trace_20250624_164236 | 82.67 | 129.82 | ~637x |
| chrome_trace_20251127_135907 | 554.47 | 109.02 | ~5086x |
| chrome_trace_20251127_151359 | 618.43 | 138.62 | ~4461x |
| chrome_trace_20260506_145919 | 387.95 | 118.43 | ~3276x |
| chrome_trace_4 | 81.40 | 101.89 | ~799x |
| chrome_trace_5 | 83.82 | 108.35 | ~774x |
| chrome_trace_1 | 555.91 | - | 仅1次调用 |
| chrome_trace_3 | 79.52 | - | 仅1次调用 |

**结论**: 首次编译耗时在 78~618ms 之间，环境差异较大（不同硬件负载/缓存状态）。稳态后 kernel 耗时仅 ~80~190us，编译开销约为 600~5000x。

`jit_compile=False` 时（`chrome_trace_20260506_135630/144923/145818`），首次调用仅 ~0.5ms，后续 ~40-60us，无编译开销。

以下统计基于 9 次 benchmark 运行（排除首次含编译的调用），仅统计 `npu::npu_aes_ctr_decrypt/encrypt` 内核事件。

### 4.2 总体统计

- **所有后续调用平均 kernel 耗时**: 107.61 us
- **整体范围**: 10.21 ~ 212.63 us (jit_compile=False 时最低可达 10us)
- **kernel 耗时与数据量无明显线性关系**: 1 字节和 16KB 数据量的耗时接近，说明 kernel 启动/调度开销占主导，真正的 AES-CTR 计算本身极快

稳态 kernel 可低至 `10~20us`（`chrome_trace_20250624_161742`），但该 trace 数据量不全。

## 5. 完整调用链耗时（wrapper 层）

`custom_aes_ctr_encrypt` 函数包含：`H2D 传输 + NPU kernel + D2H 传输`，耗时大于纯 kernel。

### 5.1 典型值

| 阶段 | 耗时 |
|------|------|
| 首次（含编译+传输） | 130ms |
| 后续（纯传输+计算） | ~0.9-1.0ms |
| 纯 kernel（稳态） | ~80-140us |

**传输开销约占 85-90%**，kernel 本身仅占 10-15%。

### 5.2 异常情况

`chrome_trace_20251127_151359` 中 wrapper 耗时出现异常（`#2=13ms, #3=17ms, #4=19ms`），但 kernel 耗时正常（85-184us），说明当时 NPU 数据传输出现延迟（可能是系统负载高或带宽竞争）。

## 6. 性能特征总结

1. **编译开销极大**：首次 JIT 编译耗时 78~618ms，稳态后仅 ~100us，编译开销 600~5000x。生产环境中应预热或关闭 JIT 编译。

2. **Kernel 启动占主导**：NPU kernel 耗时对数据量不敏感（1B ~ 16KB 均在 80~190us），说明算子受 kernel launch 延迟限制，计算吞吐远未饱和。

3. **数据传输开销大**：完整 wrapper 调用中 85%+ 的时间花在 H2D/D2H 传输上。对大数据量时建议合并传输或使用 NPU 驻留数据。

4. **环境波动**：不同运行环境下首次编译耗时差异大（80ms vs 618ms），与 NPU 负载和缓存状态有关。

5. **关闭 JIT 可大幅降低首次延迟**：`jit_compile=False` 可使首次调用从 ~80ms 降至 ~0.5ms。
